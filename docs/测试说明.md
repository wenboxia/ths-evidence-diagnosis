# 测试说明

测试分三层：**自动化测试**（`npm test`，用构造数据，不需要任何 Key，可重复执行）、**真实数据 / 真实 LLM 的故障注入测试**（本地脚本），以及**线上端到端验收**（生产 URL）。

## 1. 自动化测试：`npm test`（23 / 23 通过）

```bash
npm test     # DISABLE_SNAPSHOT=1 node --test 'tests/*.test.js'，约 2.5s（测试时关闭快照回退，保证失败场景可被观察）
```

| 文件 | 场景 | 断言要点 |
|---|---|---|
| `pipeline.test.js` | **主链路** | 25 次调用全部成功；产出 F1/F2/Q1/V1/M1/I1/D1/E2；每条 `ok` 证据都有 `sources`（带 path 与 fields）；正 + 负 + 中性 + 未知 + 过期 = 总数；季报口径被**验证**为累计值 |
| `pipeline.test.js` | **未配置 Key** | 所有调用返回 `NO_KEY`；**不产出任何正面或负面结论**；风险栏出现“数据风险” |
| `pipeline.test.js` | **接口业务错误**（财务接口返回 5003） | F1/F2 为 `error`，原因含“数据源不可用”；估值证据仍正常；公司画像仍可生成；待验证问题中有失败项 |
| `pipeline.test.js` | **数据冲突**（指标接口毛利率与报表计算值偏差 > 1pct） | X1 为 `conflict`，进入待验证问题；对照组（未篡改）为 `ok` |
| `pipeline.test.js` | **过期行情**（最新 K 线落后 20 天） | M1 为 `stale`，风险栏提示“过期”；对照组（落后 1 天）为 `ok` |
| `fuyao.test.js` | **限流重试** | 第一次 HTTP 429、第二次成功 → `ok`，`attempts=2`，之后命中缓存 |
| `fuyao.test.js` | **不可重试的错误** | 返回 2001（鉴权失败）时只请求 1 次，`attempts=1` |
| `fuyao.test.js` | **超时** | 请求不返回 → `TIMEOUT`（覆盖响应体读取阶段） |
| `fuyao.test.js` | **总时限** | 时限已过 → `BUDGET`，**不发请求** |
| `fuyao.test.js` | **失败回退缓存** | 新鲜期（10 分钟）过后实时调用失败 → 回退到上次成功结果，`cache=stale`，并带失败原因；超过 24h 则不再回退 |
| `agent.test.js` | **合规规划** | “现在能买吗？” → `compliance.flag=true`，维度包含估值；“估值贵不贵” → 优先估值；空问题 → 按公司类型的默认优先级 |
| `agent.test.js` | **校验器（7 类）** | 无引用 `no_citation`；引用不存在的 ID `bad_citation`；编造数字 `unsupported_number`；“建议买入” `compliance`；只引用缺失证据却当作事实 `unknown_as_fact`；正面证据配负面措辞 `direction_mismatch`；照抄证据的正确陈述 → 0 个严重问题 |
| `agent.test.js` | **LLM 不可用** | 无任何 LLM Key → `mode=template`，规划来源为 `rule`，所有陈述类型为 `fact` |

测试过程中发现并修复的 bug（由测试子 agent 报告）：
1. 失败调用的 `attempts` 一律显示为最大值，与实际请求次数不符，复盘时会误导 → 改为记录真实请求次数。
2. `timeoutMs < 1500` 时调用从未发出 → 1500ms 的下限只用于总时限剩余量。

## 2. 故障注入测试（真实接口、真实 LLM，本地执行）

| # | 注入方式 | 预期 | 实测结果 |
|---|---|---|---|
| A | 本地网络不可达（21 个扶摇调用全部 `fetch failed`） | 不生成任何正常结论 | ✅ 14 条证据全部为“未知”，正面 / 负面均为 0；风险栏显示“21 个工具调用失败” |
| B | 网络抖动导致部分失败（茅台 7 个财务调用失败） | 失败维度降级，其余维度正常 | ✅ 财务类证据为“未知”；估值、行情、事件正常；同行对比因目标公司财务缺失而自动跳过；有失败调用时就不做同行排名 |
| C | 主 LLM Key 错误（DeepSeek 401） | 自动切换到下一家供应商 | ✅ 规划由 Kimi k3 完成（轨迹显示：deepseek 401 → kimi 成功）。解读阶段 Kimi 31s 超时、GLM 没剩时间 → 降级为模板。**据此把切换顺序调为 DeepSeek → GLM（快）→ Kimi，并为后续供应商预留时间** |
| D | 全部 LLM Key 错误 | 规则规划 + 仅事实模板，页面明确提示 | ✅ `plan.source=rule`、`compliance.flag=true`（问题为“现在能买吗？”），`mode=template` |
| E | 线上 `/api/diagnose` 504 | 不应挂起 | 两个原因：① 响应体读取没有超时（已修复）；② 数据源对 Vercel IP 间歇性连接超时（见 F/G 的熔断与快照）。修复后线上实时数据 3–5s，0 失败 |

| F | 扶摇 Key 失效（code 2003） | 不能静默变成“正常”，也不能整页空白 | ✅ 24 个调用全部回退到快照；每条证据状态为“可能过期”，明细写明“实时调用失败（权限不足 code=2003），使用 2026-10-11 16:52 抓取的快照数据” |
| G | 数据源地址不可达（模拟网络封禁） | 熔断，迅速回退 | ✅ 探测失败后 0.6s 内整体回退快照（原先需要等满 40s 总时限） |
| H | 问答时回传被篡改的证据（把 F1 改成 +999%） | 不采用被篡改的证据 | ✅ 签名校验失败，服务端重新采集，不使用客户端传来的数据 |
| I | 线上问答复用证据 | 不重复调用数据源 | ✅ `evidence_reused=true`，问答 22.3s，校验一次通过 |
| J | 主 LLM 输出含“目标价” | 定点修复后通过 | ✅ 校验 1 处 compliance → 修复 1 条（3.0s）→ 复验通过 |

## 4. 合规与极端输入

| 输入 | 处理 |
|---|---|
| “能买吗 / 会涨吗 / 目标价多少 / 明天涨不涨” | 规则正则识别（LLM 漏判时兜底）→ 合规提示 + 改为客观维度 |
| LLM 输出含“建议买入 / 目标价 / 必涨”等 | 校验器 `compliance` 判为严重问题 → 重写；仍未通过时在原句旁标注“⚠ 未通过校验” |
| 超长问题 | 服务端截断为 300 字 |
| 空问题 | 按公司类型的默认优先级做全面诊断 |
| 非 POST 访问 `/api/ask` | 405 |
| XSS（问题或 LLM 输出中带 HTML） | 前端所有动态文本经过 `esc()` 转义 |
